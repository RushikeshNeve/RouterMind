# Phase 1 — Productization

Goal: a stranger can discover RouteMind, sign up, hit a plan limit, upgrade, and pay — with zero manual steps from us.

Work through the checklist below top to bottom. Each unchecked item is one slice: explore first (delegate to the `explorer` subagent), confirm scope, implement, verify with real tests, commit, then update this file's checkbox and the roadmap's session log before stopping. Do not start the next item in the same invocation — that's a separate `/phase-next` run, on purpose, so each slice gets a real checkpoint.

If an item turns out to already be partially done, investigate and report the actual state before either skipping or redoing work — same standing rule as Phase 0.

## Checklist

- [x] **1. Plan & Subscription schema.** `Plan(id, name, price_cents, included_requests, features_json)`, `Subscription(org_id, plan_id, status, paddle_subscription_id, paddle_customer_id, current_period_start, current_period_end)`. Seed four plans: Free, Pro, Team, Enterprise (Enterprise has no self-serve price — flag as "contact sales" in `features_json`). Schema + seed only when shipped; the `stripe_subscription_id` field named here was renamed to `paddle_subscription_id` (+ a new `paddle_customer_id`) when item 2 switched the whole phase from a planned Stripe integration to Paddle Billing — see item 2.

- [x] **2. Paddle Billing integration — subscription lifecycle.** (Originally scoped as Stripe; switched to Paddle Billing before any Stripe code existed — see docs/roadmap.md session log for why.) Wired real Paddle Billing: a checkout-transaction endpoint (`POST /v1/organizations/:organizationId/billing/checkout`, Owner-only via a new `billing.manage` permission) that creates a Paddle transaction and returns its id + the client-side token for the frontend's Paddle.js overlay (item 5's job) to open; a webhook handler (`POST /v1/webhooks/paddle`) verifying the `Paddle-Signature` header (HMAC-SHA256 over `${ts}:${rawBody}`, hand-rolled per this codebase's existing crypto convention, not the Paddle SDK) and syncing `Subscription` on `subscription.created/updated/canceled`. `PADDLE_ENVIRONMENT`/`PADDLE_API_KEY`/`PADDLE_CLIENT_TOKEN`/`PADDLE_WEBHOOK_SECRET` read from env, sandbox vs production URL never hardcoded. Paddle is the merchant of record, so nothing here calculates tax or generates invoices — Paddle owns both. Metered/overage billing untouched, flat subscription only, matching the original scope boundary.

- [x] **3. Usage metering pipeline.** `UsageSummary(org_id, period_start, period_end, request_count, token_count)` shape, computed on read directly from `RequestLog` (there is no separate `AnalyticsEvent` model in this codebase — `RequestLog` is the only table that carries token/request data; joined through `Workspace` to get `organizationId`, since `RequestLog` only has `workspaceId`). **On-read, not a nightly job**: local dev `RequestLog` had 19 rows at decision time and no job-scheduling infrastructure (cron/queue) exists anywhere in this codebase yet — a persisted `UsageSummary` table would itself be "a second counting system" the item explicitly says not to build, so this deliberately has no new table, just `GET /v1/organizations/:organizationId/billing/usage-summary` (new `billing.read` permission, Admin+Owner) computing live. Only `status = "success"` requests count as billable usage (an interpretation decision, not explicit in the spec). Revisit with a cache/nightly job if `RequestLog` volume ever shows up in latency profiling.

- [x] **4. Plan-limit enforcement via the policy engine.** Added a `plan_limit` rule type to `evaluatePolicy()` (`packages/policy-engine`), same engine as `budget`/`model_restriction`/`cost_cap`. Unlike those three (admin-configured, a real `Policy` row), `plan_limit` is derived automatically from the org's `Plan.includedRequests` — no Policy CRUD row to create/maintain. `PrismaPolicyRuleLookup.findRulesForWorkspace()` synthesizes it on every call (org's `Subscription`+`Plan`, or a fallback to the seeded "Free" plan by name if the org has no `Subscription` row yet), embedding `{maxRequests, currentRequestCount}` (via item 3's `computeUsageSummary()`) directly in the synthetic rule's `ruleJson` — still funneled through the one `evaluatePolicy()` call, no separate enforcement path. Added a new `"workspace"` `PolicySubjectType` (applies unconditionally, no subjectId to match) since `plan_limit` isn't scoped to a role/user/api_key. Blocked requests get a distinct `PLAN_LIMIT_EXCEEDED` reason, same pattern as `MODEL_RESTRICTED`/`COST_CAP_EXCEEDED`/`BUDGET_EXCEEDED`.

- [x] **5. Self-serve billing UI.** Dashboard screen (org-level, Admin read / Owner manage): current plan, usage against included requests, upgrade buttons (calls item 2's checkout endpoint, then opens Paddle.js's overlay with the returned transaction id), a note that payment method/invoices are Paddle-hosted (nothing of ours to render). **Real gap closed first, not worked around**: the dashboard had no way to know a workspace's `organizationId` at all (both billing endpoints are org-scoped) and no endpoint listed plans or an org's current plan+usage together — extended `GET /v1/workspaces/:id/me` with `organizationId` (already fetched by every page via `usePermissions()`, so free for every screen going forward) and added `GET /v1/plans` (public) + `GET /v1/organizations/:id/billing/overview` (`billing.read`) to close both gaps as part of this slice. Enterprise (and any future contact-sales-only tier) renders as a "Contact sales" link instead of a checkout button, driven by `featuresJson.contactSales`. **Not live-verified**: the Paddle.js overlay call (`Paddle.Environment.set`/`Paddle.Initialize`/`Paddle.Checkout.open`) is implemented against Paddle's documented client API but has not been exercised against a real Paddle sandbox account, same standing caveat as item 2's backend client.

- [x] **6. Model discovery & sync.** `ModelCatalog(provider, model, capabilitiesJson, pricingJson, lastSyncedAt)`, platform-level (no workspaceId, same category as `Plan`). `POST /v1/workspaces/:id/models/discover` (reused the existing `models.manage` permission — no new permission needed) calls each provider's real list-models endpoint (OpenAI/Groq share one OpenAI-compatible implementation; Anthropic and Gemini each their own) using the workspace's decrypted stored credential, upserting `ModelCatalog` rows. In `PROVIDER_MODE=mock` (this environment's default), no credential is needed at all — discovery reads the static, hand-curated `modelRegistry` instead (and reuses its rich capability fields — `supportsCode`, `costTier`, etc. — for `capabilitiesJson`, matching the architecture review's own predicted pitfall that provider list-models APIs return little beyond a model id). Also added `GET /v1/models/catalog` (public, same category as `GET /v1/plans`). **Real near-miss avoided**: `apps/api/src/routes/models.ts` already existed (the OpenAI-compat `GET /v1/models` endpoint) — almost overwrote it blindly; read it first and extended the same file/function instead of creating a naming collision. Dashboard: replaced `/dashboard/models`'s pure demo-data stub with a real page (provider discover buttons + a live catalog table) — the phase item's own wording ("a button on the existing model-access screen") assumed a wired screen that, like item 5's org-context gap, turned out not to actually exist; closed as part of this slice rather than deferred, scoped narrowly to discovery+display (no enable/disable toggle UI, since the existing model-access mutation route in `onboarding.ts` is still user-scoped, not workspace-scoped — a separate, real, pre-existing gap, flagged not fixed here). **Not live-verified**: the four real provider list-models calls have not been exercised against real credentials in this environment, same standing caveat as items 2 and 5.

- [x] **7. Workspace/API-key scoped analytics.** Audit found a real, confirmed cross-tenant confidentiality gap, not a "confirm it's already covered" no-op: all 7 `/v1/analytics/*` routes and `GET /v1/resilience/provider-attempts` had **zero** authentication and accepted `workspaceId`/`userId` as unvalidated optional query params — any caller (no API key required) could read any workspace's cost/request/model/error/provider-attempt data by passing a different id. The service layer (`analytics-service.ts`) already filtered correctly by `workspaceId` when given one; the gap was entirely the route layer never requiring one. Fixed by migrating all 8 routes to `/v1/workspaces/:workspaceId/analytics/*` and `/v1/workspaces/:workspaceId/resilience/provider-attempts`, gated with the existing `analytics.read` permission (already granted to every role including Viewer — no new permission needed) plus `ensureSameWorkspace`; `workspaceId` is now always derived from the validated path param, never the query string, which also makes the secondary `userId` filter safe-by-construction. `/v1/resilience/circuit-breakers*` and `/v1/health/*` were deliberately left unscoped — they're platform-wide operational state with no tenant dimension to violate; gating them would be cosmetic, not a real fix. Dashboard's `useDashboardData()` (`apps/dashboard/src/lib/api.ts`) now resolves the active workspace via `getActiveWorkspace()` and calls the new scoped paths with `credentials: "include"` (previously sent zero auth and displayed platform-wide aggregate data to every viewer, regardless of role/workspace — a direct symptom of the same gap, not real per-tenant reporting despite hitting real endpoints); shows a clear "no active workspace" message via the existing demo-data fallback path if none is set. 15 new integration tests (11 in `analytics.test.ts`, 4 in a new `resilience.test.ts`): per-route auth/role coverage, unauthenticated 401, cross-workspace-key 403, and a dedicated isolation test proving one workspace's requests never appear in another's summary even when both share the same underlying log store. `createPrismaWorkspaceTestApp` (shared RBAC test fixture) extended with optional in-memory log-store overrides to make this provable without a full Postgres-backed `PrismaAnalyticsService` test. **Flagged, not fixed here — out of this item's declared scope**: `apps/api/src/routes/evaluations.ts` has the identical unscoped-route shape (grepped: zero `workspaceId` references anywhere in the file) and is exposed via the same `useDashboardData()` bundle; added as item 9 below rather than fixed inline, per this project's standing practice of surfacing newly-found gaps as their own checklist item instead of silently absorbing them into unrelated work.

- [ ] **8. Pricing page.** Public-facing page (marketing site or a `/pricing` dashboard route, whichever already exists) stating the four plans' real prices/limits — no "contact sales" for Free/Pro/Team. This directly supports the "predictable pricing" positioning from the market research; the numbers must match what the `Plan` table actually enforces, not be a separate hardcoded claim.

- [ ] **9. Workspace-scope `/v1/evaluations/*`.** Found while auditing item 7, flagged rather than fixed inline (out of that item's declared scope): `apps/api/src/routes/evaluations.ts`'s three routes (`GET /v1/evaluations/datasets`, `/runs`, `/scores`) have zero `workspaceId` references anywhere in the file — no authentication, no tenant scoping, same unscoped-route shape item 7 just fixed for analytics/provider-attempts. Also reached by the dashboard's `useDashboardData()` bundle, so the Evaluations page currently shows the same platform-wide, cross-tenant data problem. Apply the identical fix pattern: workspace-scoped path, `requirePermission`/`ensureSameWorkspace` gating, dashboard update to call the scoped path with credentials.

## Exit criteria for Phase 1

A person who has never spoken to us can: sign up → hit the Free tier's request limit → see a clear upgrade prompt with real pricing → pay with a real (test-mode) credit card → immediately have the limit lifted — end to end, with no manual intervention from us at any step. Write this as an actual Playwright/integration test before declaring Phase 1 done, same standard as Phase 0's exit-criteria test.
