# Phase 1 — Productization

Goal: a stranger can discover RouteMind, sign up, hit a plan limit, upgrade, and pay — with zero manual steps from us.

Work through the checklist below top to bottom. Each unchecked item is one slice: explore first (delegate to the `explorer` subagent), confirm scope, implement, verify with real tests, commit, then update this file's checkbox and the roadmap's session log before stopping. Do not start the next item in the same invocation — that's a separate `/phase-next` run, on purpose, so each slice gets a real checkpoint.

If an item turns out to already be partially done, investigate and report the actual state before either skipping or redoing work — same standing rule as Phase 0.

## Checklist

- [x] **1. Plan & Subscription schema.** `Plan(id, name, price_cents, included_requests, features_json)`, `Subscription(org_id, plan_id, status, paddle_subscription_id, paddle_customer_id, current_period_start, current_period_end)`. Seed four plans: Free, Pro, Team, Enterprise (Enterprise has no self-serve price — flag as "contact sales" in `features_json`). Schema + seed only when shipped; the `stripe_subscription_id` field named here was renamed to `paddle_subscription_id` (+ a new `paddle_customer_id`) when item 2 switched the whole phase from a planned Stripe integration to Paddle Billing — see item 2.

- [x] **2. Paddle Billing integration — subscription lifecycle.** (Originally scoped as Stripe; switched to Paddle Billing before any Stripe code existed — see docs/roadmap.md session log for why.) Wired real Paddle Billing: a checkout-transaction endpoint (`POST /v1/organizations/:organizationId/billing/checkout`, Owner-only via a new `billing.manage` permission) that creates a Paddle transaction and returns its id + the client-side token for the frontend's Paddle.js overlay (item 5's job) to open; a webhook handler (`POST /v1/webhooks/paddle`) verifying the `Paddle-Signature` header (HMAC-SHA256 over `${ts}:${rawBody}`, hand-rolled per this codebase's existing crypto convention, not the Paddle SDK) and syncing `Subscription` on `subscription.created/updated/canceled`. `PADDLE_ENVIRONMENT`/`PADDLE_API_KEY`/`PADDLE_CLIENT_TOKEN`/`PADDLE_WEBHOOK_SECRET` read from env, sandbox vs production URL never hardcoded. Paddle is the merchant of record, so nothing here calculates tax or generates invoices — Paddle owns both. Metered/overage billing untouched, flat subscription only, matching the original scope boundary.

- [x] **3. Usage metering pipeline.** `UsageSummary(org_id, period_start, period_end, request_count, token_count)` shape, computed on read directly from `RequestLog` (there is no separate `AnalyticsEvent` model in this codebase — `RequestLog` is the only table that carries token/request data; joined through `Workspace` to get `organizationId`, since `RequestLog` only has `workspaceId`). **On-read, not a nightly job**: local dev `RequestLog` had 19 rows at decision time and no job-scheduling infrastructure (cron/queue) exists anywhere in this codebase yet — a persisted `UsageSummary` table would itself be "a second counting system" the item explicitly says not to build, so this deliberately has no new table, just `GET /v1/organizations/:organizationId/billing/usage-summary` (new `billing.read` permission, Admin+Owner) computing live. Only `status = "success"` requests count as billable usage (an interpretation decision, not explicit in the spec). Revisit with a cache/nightly job if `RequestLog` volume ever shows up in latency profiling.

- [x] **4. Plan-limit enforcement via the policy engine.** Added a `plan_limit` rule type to `evaluatePolicy()` (`packages/policy-engine`), same engine as `budget`/`model_restriction`/`cost_cap`. Unlike those three (admin-configured, a real `Policy` row), `plan_limit` is derived automatically from the org's `Plan.includedRequests` — no Policy CRUD row to create/maintain. `PrismaPolicyRuleLookup.findRulesForWorkspace()` synthesizes it on every call (org's `Subscription`+`Plan`, or a fallback to the seeded "Free" plan by name if the org has no `Subscription` row yet), embedding `{maxRequests, currentRequestCount}` (via item 3's `computeUsageSummary()`) directly in the synthetic rule's `ruleJson` — still funneled through the one `evaluatePolicy()` call, no separate enforcement path. Added a new `"workspace"` `PolicySubjectType` (applies unconditionally, no subjectId to match) since `plan_limit` isn't scoped to a role/user/api_key. Blocked requests get a distinct `PLAN_LIMIT_EXCEEDED` reason, same pattern as `MODEL_RESTRICTED`/`COST_CAP_EXCEEDED`/`BUDGET_EXCEEDED`.

- [x] **5. Enterprise (and any future contact-sales-only tier) renders as a "Contact sales" link instead of a checkout button, driven by `featuresJson.contactSales`. **Not live-verified**: the Paddle.js overlay call (`Paddle.Environment.set`/`Paddle.Initialize`/`Paddle.Checkout.open`) is implemented against Paddle's documented client API but has not been exercised against a real Paddle sandbox account, same standing caveat as item 2's backend client.

- [x] **6. - [x] **7. Workspace/API-key scoped analytics.** Audit found a real, confirmed cross-tenant confidentiality gap, not a "confirm it's already covered" no-op: all 7 `/v1/analytics/*` routes and `GET /v1/resilience/provider-attempts` had **zero** authentication and accepted `workspaceId`/`userId` as unvalidated optional query params — any caller (no API key required) could read any workspace's cost/request/model/error/provider-attempt data by passing a different id. The service layer (`analytics-service.ts`) already filtered correctly by `workspaceId` when given one; the gap was entirely the route layer never requiring one. Fixed by migrating all 8 routes to `/v1/workspaces/:workspaceId/analytics/*` and `/v1/workspaces/:workspaceId/resilience/provider-attempts`, gated with the existing `analytics.read` permission (already granted to every role including Viewer — no new permission needed) plus `ensureSameWorkspace`; `workspaceId` is now always derived from the validated path param, never the query string, which also makes the secondary `userId` filter safe-by-construction. `/v1/resilience/circuit-breakers*` and `/v1/health/*` were deliberately left unscoped — they're platform-wide operational state with no tenant dimension to violate; gating them would be cosmetic, not a real fix. Dashboard's `useDashboardData()` (`apps/dashboard/src/lib/api.ts`) now resolves the active workspace via `getActiveWorkspace()` and calls the new scoped paths with `credentials: "include"` (previously sent zero auth and displayed platform-wide aggregate data to every viewer, regardless of role/workspace — a direct symptom of the same gap, not real per-tenant reporting despite hitting real endpoints); shows a clear "no active workspace" message via the existing demo-data fallback path if none is set. 15 new integration tests (11 in `analytics.test.ts`, 4 in a new `resilience.test.ts`): per-route auth/role coverage, unauthenticated 401, cross-workspace-key 403, and a dedicated isolation test proving one workspace's requests never appear in another's summary even when both share the same underlying log store. `createPrismaWorkspaceTestApp` (shared RBAC test fixture) extended with optional in-memory log-store overrides to make this provable without a full Postgres-backed `PrismaAnalyticsService` test. **Flagged, not fixed here — out of this item's declared scope**: `apps/api/src/routes/evaluations.ts` has the identical unscoped-route shape (grepped: zero `workspaceId` references anywhere in the file) and is exposed via the same `useDashboardData()` bundle; added as item 9 below rather than fixed inline, per this project's standing practice of surfacing newly-found gaps as their own checklist item instead of silently absorbing them into unrelated work.

## Exit criteria for Phase 1

A person who has never spoken to us can: sign up → hit the Free tier's request limit → see a clear upgrade prompt with real pricing → pay with a real (test-mode) credit card → immediately have the limit lifted — end to end, with no manual intervention from us at any step.

**Done** (`apps/api/src/routes/phase1-exit-criteria.test.ts`): a real integration test, same standard as Phase 0's exit-criteria test (a Vitest integration test driving real routes via `app.inject()` against real Postgres, not a browser-driven Playwright test — matching Phase 0's own precedent). Drives real magic-link signup, a real self-issued API key, real Policy-engine enforcement against the real seeded Free plan's 10,000-request limit, the real `GET /v1/plans`/`billing/overview` data an upgrade prompt renders from, a real checkout call against the real seeded Pro plan, and a real, correctly HMAC-signed `POST /v1/webhooks/paddle` delivery — then proves the very next request succeeds under Pro's higher limit with no restart and no manual step. The one thing this environment cannot do is drive a browser through Paddle's actual hosted checkout UI, since no live Paddle sandbox credentials exist here (items 2/5's standing caveat) — "pay with a real credit card" is represented by simulating the one external event Paddle itself sends on a real payment (a signed `subscription.created` webhook), which is how this backend learns about payment outcomes in production too, since it never sees a card number either way.
