## Checklist

- [x] **1. Harden BYO Router Model: explicit, surfaced fallback behavior.** Already done, verified before writing this checklist rather than assumed: `routemind.routing.reason` (and `routingMetadata.configSource`) are populated on every `/v1/chat/completions` response, with four distinct, exported fallback-reason constants (`LLM_ROUTING_DISABLED_REASON`, `LLM_ROUTING_STRATEGY_SKIP_REASON`, `LLM_ROUTING_CALL_FAILED_REASON`, `LLM_ROUTING_NO_CANDIDATE_MATCH_REASON` in `packages/routing/src/index.ts`) so degraded routing is never silently collapsed into one generic string — this was Phase 0 work (2026-07-19 session log entries) that already satisfies this Phase 2 Ship-list line item in full. Nothing shipped in this slice.

- [x] **2. Rate limiting distinct from budgets.** Already done, verified before writing this checklist: `apps/api/src/infrastructure/rate-limiter.ts` (`RedisRateLimiter`/`InMemoryRateLimiter`) is live-wired into `/v1/chat/completions` (`chat-completions.ts` lines ~251-274), runs _before_ cost-guardrail/plan-limit checks, sets `x-ratelimit-limit`/`-remaining`/`-reset` headers, and returns a real `429 rate_limit_exceeded` — genuinely protecting the platform independent of a customer's willingness to pay, distinct from `Policy`'s `budget`/`plan_limit` rule types. **Known limitation, not blocking**: the limit is a hardcoded 100 requests/hour per API key, not configurable per plan tier or per workspace — the roadmap's own wording only asked for "distinct from budgets," which this already satisfies; per-tier limits are a future refinement, not required to check this off. Nothing shipped in this slice.

- [x] **3. Data retention / prompt-logging controls, configurable per workspace.** Shipped: `Workspace.promptLoggingEnabled` (default `true`, purely additive migration `20260816175635_add_workspace_prompt_logging_enabled`) plus a `PromptLoggingPolicyLookup` service consulted by `chat-completions.ts` before every exact-cache read/write. **Design decision, made during the slice as flagged**: since `LLMResponseCache.responseJson` is confirmed (by direct code reading of the cache-hit path) to be the literal response body replayed verbatim on a cache hit — not just observability data — disabling prompt logging for a workspace skips response caching **entirely** for that workspace, rather than attempting to persist a redacted `promptText` while keeping `responseJson`. Partial redaction would have left the exact same sensitive-data-retention problem under a different field name; full cache bypass is a hard guarantee, not a best-effort one. `buildCachePlan()`/`shouldStoreCache()` both gained a `promptLoggingEnabled` parameter (default `true`, matching every other addition to this pipeline) that short-circuits to the same "no lookup, no store" path as `mode: "disabled"`. New `GET`/`PATCH /v1/workspaces/:workspaceId/prompt-logging` routes (new `dataRetention.read`/`dataRetention.manage` permissions, Admin+Owner, mirroring `router.read`/`router.manage`'s placement exactly), writing to the existing `workspace.update` audit action rather than inventing a new one, and a minimal dashboard toggle at `/dashboard/data-retention` (new nav item, `dataRetention.read`-gated) — the first dashboard settings screen for a single boolean rather than a CRUD list, so it reuses `Card`/`CardHeader` but not `router-config`'s form/table pattern. **Verified, not just implemented**: `createPrismaWorkspaceTestApp` extended with `cacheService`/`promptLoggingPolicyLookup` overrides so tests can inspect the cache directly (previously only `buildApp()` itself exposed this); a new `prompt-logging.test.ts` proves RBAC gating (12 tests) and, via two real `/v1/chat/completions` round trips against a real Postgres-backed `InMemoryCacheService`, that a workspace with logging disabled genuinely persists zero cache entries across two identical requests (no second-request cache hit either) while the default-enabled case caches and hits normally. Full `apps/api` suite 304/304 passing, `apps/dashboard` `tsc --noEmit` and `next build` both clean (`/dashboard/data-retention` compiles at 1.38 kB), lint and prettier clean. **Not done, explicitly out of scope**: the local migration has not yet been applied to production (still pending, same as every schema change in this session until explicitly requested); no retention-policy table beyond the single boolean (e.g. "retain for N days" instead of on/off) — the roadmap's own wording only asked for a per-workspace control, which this satisfies as a binary toggle.

- [x] **4. A genuinely honest pricing/trust page: explicit data-handling statements.** Shipped: a new "Data & Trust" section (`apps/website/src/components/landing/data-handling.tsx`) on the public homepage, wired in right after Pricing, linked from the navbar (`#data-handling`), and cross-referenced by a short note added directly to the pricing page itself ("Prompt logging is a workspace-level toggle included on every plan, on by default — see Data & Trust for what that actually does"), per this item's own literal wording that the pricing page should state this plainly. Four concrete claims, each chosen because it maps to a feature verified live and tested in this repo, not aspirational copy: (1) the per-workspace prompt-logging toggle from item 3, worded precisely — "skips response caching entirely," not a vaguer "we protect your data"; (2) provider credentials encrypted at rest and workspace-scoped, matching `CREDENTIAL_ENCRYPTION_KEY`/`encryptCredential`/`decryptCredential`'s real behavior; (3) the audit log's same-transaction guarantee, matching the real `writeAuditEvent(tx, ...)` pattern verified by a genuine rollback test back in Phase 0; (4) the declarative policy engine's live enforcement (budget/model_restriction/cost_cap/plan_limit), matching `evaluatePolicy()`'s real wiring into `CostGuardrailService`. **Deliberately not claimed**: "we never see your keys" — investigated and rejected as overclaiming, since the gateway necessarily decrypts a workspace's provider credentials server-side to make the actual provider call on the customer's behalf; the shipped copy says credentials are encrypted at rest and workspace-scoped instead, which is precisely true rather than aspirationally true. **Verified**: `apps/website` `tsc --noEmit` and `next build` both clean, root `npm run lint`/`format:check` clean; live-browser-verified via Playwright against the real dev server (not just a build check) — screenshotted the new section rendering correctly, confirmed the pricing-page note and its link text render with the right href (`#data-handling`), and confirmed "Data & Trust" appears in the desktop navbar between Pricing and Architecture at a 1440px viewport. **Not done, out of scope**: no separate dedicated `/trust` route — the item's own wording said "and/or a dedicated trust/security page," and a same-page section satisfies that for a site this size without adding routing/nav-architecture overhead; the pre-existing `TrustSection` (tech-stack badges) was left untouched rather than merged into this new section, since it's a different, still-valid trust signal (what the system is built with, not how it handles data).
